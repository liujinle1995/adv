# 已知限制、风险与备选方案

## 1. 先说清楚：这个产品**不是**什么

| 常见误解 | 事实 |
|---|---|
| "是个安卓虚拟机" | 不是。这是**用户态应用级虚拟化**：虚拟 App 与宿主**同一个 Linux UID**，共享宿主进程的权限边界 |
| "能防住恶意 App" | 不能。沙箱内的恶意 App 理论上可攻击宿主进程、读宿主文件（同 UID），也能攻击其它实例。真正隔离需要内核/虚拟化（AVF、VM），而它们目前跑不了第三方 GUI 应用 |
| "能保证账号安全/防封" | 不能。签名变更、设备指纹变化都可能触发服务端风控。**我们不做指纹伪造**（伪造本身违反多数 App 条款，且会让封号风险更高） |
| "支持所有 App" | 不支持。加固壳、签名自校验、Play Integrity、依赖系统签名的 App 都会失败 |
| "性能接近原生" | 不一定。引擎内启动通常比原生慢（需实测基线），内存占用更高 |

## 2. 硬限制清单（无法通过工程手段绕过）

| # | 限制 | 原因 | 用户可见的后果 |
|---|---|---|---|
| L1 | 32 位 App 在纯 64 位设备/引擎上不能跑 | 设备内核与引擎产物均无 32 位支持 | 导入时直接判 `ABI_MISMATCH`，不要让用户白等 |
| L2 | 加固壳 App 大概率失败 | 壳会检测调试/虚拟环境/进程名 | 明确"该类应用不支持" |
| L3 | 签名变更导致 SDK 功能失效 | 微信/QQ/支付宝/地图/Firebase 等绑定包名+签名 | UI 标注"登录/支付/推送可能不可用" |
| L4 | 服务端强制升级 | 服务端策略，不由客户端决定 | 无法解；属于产品需求层面的风险 |
| L5 | targetSdk 过低的包在老 API 上崩 | App 自身调用已移除/变更的 API | 记录为兼容性 `WARN` |
| L6 | 系统级完整性校验（Play Integrity / SafetyNet） | 依赖系统证明链 | 会失败，且不应尝试绕过 |
| L7 | 厂商 ROM 省电策略杀子进程 | 系统行为 | 后台保活不保证；提供引导 |
| L8 | 无 Root 无法读取其它 App 私有目录 | Linux 权限 | 这是**优点**（数据天然隔离），也意味着无法"迁移宿主原 App 数据"到沙箱 |

## 4. 备选方案（按"引擎路线失败时"的优先级）

### 备选 1：改包名重打包（单一 App 场景最实用）

**流程**

```bash
apktool d target-low.apk -o out
# 1) AndroidManifest.xml: package="com.vendor.app" → "com.adv.clone.<hash>"
# 2) 同步改 authorities / provider android:name / 自定义权限名（凡是带原包名的）
# 3) 若 App 有 hardcode 包名的地方（少见但存在），需 smali 层改动 —— 这一步风险最高
apktool b out -o patched.apk
zipalign -p -f 4 patched.apk aligned.apk
apksigner sign --ks my.jks --out final.apk aligned.apk
adb install final.apk
```

| 优点 | 缺点 |
|---|---|
| 0 引擎依赖、系统级 UID 隔离、数据绝对分离、性能原生 | 必须修改目标 APK；签名校验/加固/完整性校验的 App 直接失败；每个 App 每个版本单独适配；可能违反第三方 App 服务条款 |
| 适合"就一款 App 的低版本" | 不适合做成通用产品 |

**结论：作为本项目第 1 版之前的过渡手段是合理的，但要说清"这不是虚拟化"。**

### 备选 2：工作资料 / 多用户（Island、Shelter 思路）

- 用 `DevicePolicyManager` 创建 managed profile（需用户授权，非 Root）。
- **优点**：系统级隔离、无需改 APK、无需引擎。
- **关键未知**：同包名**不同签名**在工作资料里是否被拒（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。PMS 的包设置跨用户共享，**大概率失败** → 必须先实测（1 小时可验证），不要直接承诺。

### 备选 3：云手机 / 远程真机

- 服务端跑真实 Android 8/9 容器或真机，客户端只做投屏。
- 优点：兼容性最好（就是真机）、隔离最强、可跑老系统。
- 缺点：成本（每实例每月费用）、延迟、隐私（账号在云端）、离线不可用。
- 定位：**"必须支持某款顽固 App"时的兜底**，尤其老 App 需要老系统时。

### 备选 4：AVF + Microdroid（未来可期，现在不可用）

- 只在支持 pKVM 的 ARM64 设备上、且 API 不在 `bootclasspath`、无 GUI 输出。
- 现在能做的只有"把不涉及界面的敏感计算放进 pVM"，**与本项目需求无关**。
- 若未来 Android 把"虚拟显示 + 输入注入"开放给第三方，这条路才会成为最优解。**跟踪，不投入。**

## 6. "什么情况下应该放弃这个项目"

诚实的止损条件（任一成立即应重新评估需求）：

1. 目标 App 在引擎内**登录必失败**，且原因确认是签名/完整性校验；
2. 目标机型（用户主力机）Android 版本高于可用引擎的支持上限，且预算无法购买商业授权；
3. 需要"真正隔离"（对抗恶意 App）——此时应改用整机虚拟机/云手机，而不是应用虚拟化；
4. 需要"批量支持任意 App"——应用级虚拟化的兼容性是逐 App 积累的，无法承诺。

在这种情况下，**宁可交付"改包名重打包 + 明确说明"的方案，也不要把一个跑不起来的沙箱包装成产品。**
